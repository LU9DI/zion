# Disposable CometBFT two-project PoC: application, proof verifier, and fault-injection contract

Status: **implementation-ready test specification only**. This document does not select CometBFT for Zion and does not authorize a workflow, runtime integration, dependency, infrastructure, or production change.

Scope: PR #68; companion to `COMETBFT_PROJECT_ISOLATION_FEASIBILITY_SPIKE.md`, `COMETBFT_0_38_26_ABCI_COMMIT_CONTRACT_AUDIT.md`, and `PROJECT_TRUSTED_CHECKPOINT_AND_STATE_SYNC_SPEC.md`.

## 1. Objective and strict boundaries

Define the smallest reproducible experiment that can distinguish:

1. deterministic ABCI application execution;
2. a real CometBFT consensus commit;
3. independent verification of the resulting commit evidence; and
4. fault isolation between two project-scoped test networks.

The PoC must be disposable and test-only. It must not connect to Zion production peers, official launchers, Neon/PostgreSQL, user accounts, invitation state, current project data, production keys, or any hosted service required for correctness. It must not expose a public RPC/P2P listener.

The first topology is two independent GitHub-hosted runner VMs, one per project, each with its own local Docker daemon and four validator containers. This tests separate VM/daemon failure domains within one CI provider; it does **not** prove independent real-world operators or cloud-control-plane independence.

Pinned source input for the initial experiment: CometBFT `v0.38.26`, peeled commit `94d77f9f51a72e2b7d832798859f6222f08028f8`. Recheck upstream support/security status before execution. The pin is not an adoption decision.

## 2. Test ABCI application contract

Implement one small test-only application, compiled into the disposable harness and launched separately for alpha and beta. It must expose the ABCI++ methods required by the pinned CometBFT release and must not contain Zion product logic.

### 2.1 Genesis

Each application receives a canonical genesis document containing:

- protocol identifier: `zion-isolation-poc/v1`;
- immutable project identifier: exactly `project-alpha` or `project-beta`;
- unique chain ID, distinct across projects;
- genesis nonce and genesis-state digest, distinct across projects;
- initial state schema version;
- fixed application limits (maximum transaction bytes, key bytes, value bytes, and operations per block);
- initial application state: empty key/value map and sequence zero.

The application must reject startup if its configured project ID, chain ID, genesis digest, or schema version does not match its compiled/test configuration. Do not derive project identity from a mutable environment variable after startup.

### 2.2 Transaction envelope

Use a strict, versioned, canonical binary envelope. Do not rely on JSON object key order or permissive parser behavior. The envelope fields are:

- magic and protocol version;
- project ID;
- operation ID (16 or 32 random bytes generated by the test client; uniqueness is checked in application state);
- operation type;
- key and value byte strings with explicit length prefixes;
- expected prior sequence;
- optional expected prior value digest.

Reject unknown versions/types, non-canonical encodings, trailing bytes, duplicate fields, oversized fields, invalid UTF-8 where text is required, wrong project IDs, and malformed operation IDs. Enforce the same parser and limits in proposal validation and final execution.

Only two state-changing operations are needed:

- `PUT`: set one bounded key/value pair if the expected prior sequence matches;
- `DELETE`: remove one existing key if the expected prior sequence matches.

A deterministic `NOOP` can be included for control experiments. No transaction may contain a clock value, local path, process ID, random value generated by the application, network result, or host-specific data.

### 2.3 Deterministic state transition

State consists of:

- project ID and genesis digest;
- monotonically increasing committed application sequence;
- bounded key/value map;
- operation-ID to immutable result mapping (idempotency);
- schema version.

For each committed transaction, the application must:

1. validate the canonical envelope and project binding;
2. check the operation ID;
3. if already applied with identical bytes, return the exact prior result without applying twice;
4. if the same operation ID is reused with different bytes, reject as equivocation/replay conflict;
5. verify the expected sequence and optional prior-value digest;
6. apply the operation deterministically;
7. increment the sequence only on successful state mutation;
8. store the immutable operation result in the same state transition.

Rejected transactions must not mutate application state or advance its application sequence. All replicas receiving the same committed bytes and prior state must return byte-identical results and the same app hash.

### 2.4 App hash and persistence

Define and version a canonical state serialization: sorted raw key bytes, explicit lengths, fixed-width integers, and domain-separated hashes. The application hash must commit to the project ID, genesis digest, schema version, sequence, key/value state, and idempotency records. Publish test vectors for empty state, one PUT, one DELETE, duplicate operation, and rejected operation.

The application must implement a crash-safe persistence boundary for its own state. Persist the state snapshot, committed height, app hash, sequence, and idempotency results atomically (temporary file + fsync + atomic rename + directory fsync, or a separately reviewed transactional store). On recovery, validate checksum, schema, project identity, and consistency between stored height and state. Corruption or ambiguous partial state must fail closed; never silently reset to genesis.

Do not claim that this makes the application store and CometBFT block store one physical atomic transaction. The adapter must follow the pinned ABCI replay contract and be fault-tested at each persistence milestone.

### 2.5 ABCI method behavior

- `CheckTx`: bounded syntactic validation and cheap project/version checks only; it is not a commitment.
- `PrepareProposal`: deterministic filtering/ordering policy based only on supplied candidate transactions and fixed limits. It must not read wall-clock, host state, or external services.
- `ProcessProposal`: deterministic accept/reject from the proposal bytes and last committed application state; it must not persist candidate state.
- `FinalizeBlock`: execute the decided block deterministically against a disposable candidate copy, produce transaction results and the resulting app hash/validator updates; do not emit external side effects.
- `Commit`: persist the already-finalized application state using the crash-safe boundary; return only the fields supported by the pinned ABCI schema. Do not expect a quorum certificate or app hash from the Commit response.
- `Info`: report the exact last durably committed application height and app hash; never report ahead of durable application state.
- `Query`: read-only, bounded, and scoped to the configured project.

No validator updates are required for the baseline application. Committee reconfiguration is a separate experiment and must not be smuggled into the first functional test.

## 3. Independent commit-proof verifier

A test result is not accepted merely because an RPC endpoint says a block committed or because the local ABCI callback returned successfully.

### 3.1 Evidence bundle

For each accepted height, export a self-contained, immutable evidence bundle containing:

- chain ID and project ID;
- signed header and block ID;
- CometBFT commit object and all commit signatures;
- validator set required to verify that commit;
- validator-set hash and relevant header fields;
- trusted checkpoint (height, signed header/hash, validator set, trust period, trust level);
- validator-set transition evidence from the checkpoint to the target height;
- application app hash and transaction results;
- canonical transaction bytes and their hashes;
- CometBFT version/commit, application binary digest, and harness source revision.

The bundle must be generated from the test node's block store/export path, not reconstructed from an untrusted summary response. Preserve original bytes.

### 3.2 Verification modes

Provide two explicit verification modes and report which was used:

**Mode A — commit verification at a known validator set.** Verify the target commit's chain ID, height, block ID, signatures, and voting power using the exact validator set for that height and CometBFT's upstream commit-verification primitives. Require strictly more than two-thirds of total voting power. Reject duplicate/unknown signers, invalid signatures, wrong block IDs, wrong chain IDs, wrong heights, and insufficient voting power.

**Mode B — light-client verification from a trusted checkpoint.** Start from an independently authenticated checkpoint, then use the pinned CometBFT light-client verification logic to verify signed headers and validator-set transitions up to the target. Apply the configured trusting period, trust level, adjacent/non-adjacent verification rules, and witness requirements. Do not accept a checkpoint obtained solely from the same RPC endpoint being verified.

Mode A proves a commit relative to a supplied validator set; it does not authenticate that validator set. Mode B proves continuity relative to its trust anchor; it does not solve the initial Zion genesis/governor trust ceremony. The PoC must not claim otherwise.

### 3.3 Negative verifier tests

The verifier must reject at least:

1. one altered signature byte;
2. one removed signature causing voting power to fall to or below two-thirds;
3. a signature from an unknown validator;
4. a duplicated signature counted twice;
5. a changed block ID or app hash;
6. a wrong chain ID or height;
7. a validator-set hash mismatch;
8. an invalid validator-set transition;
9. an expired trusting period;
10. a stale or mismatched trusted checkpoint;
11. a target header with insufficient trust overlap;
12. a valid certificate for alpha presented as beta evidence.

The verifier must produce a machine-readable reason code and must not downgrade failed verification to a warning or accept an RPC-provided boolean.

## 4. Fault-injection mechanisms and scope

Use only deterministic, explicitly logged controls. Every injection records project, validator/container, start/end timestamp, command, exit status, and resulting height/app-hash series.

### 4.1 Process and quorum faults

- Stop one validator: with four validators and f=1, the network should retain the ability to commit if the remaining three are healthy.
- Stop two validators: the network must stop committing new blocks; no local fallback or application-side commit is permitted.
- Stop all validators in beta: alpha must continue committing and verifying.
- Restart a stopped validator: it must catch up from its own network and recover without reading the other project's files or state.

These are crash/availability faults, not Byzantine behavior.

### 4.2 Network faults

Use per-project Docker networks and controlled network rules to:
- isolate one validator from the other three;
- partition beta into 2+2 and confirm no side commits;
- restore connectivity and verify one canonical history;
- block all beta peer traffic while alpha continues.

A 2+2 partition is below quorum for either side in a four-validator, f=1 network. Do not describe simple packet loss or process stops as proof of Byzantine safety.

### 4.3 Storage faults

On disposable copies only:
- terminate the ABCI application between FinalizeBlock and Commit;
- terminate immediately after application fsync but before the response is observed;
- truncate/corrupt the application journal or snapshot;
- simulate disk-full and write/fsync failure where the runner supports it;
- restart CometBFT and the application in each interrupted state.

Expected behavior: deterministic replay or fail-closed recovery under the documented ABCI contract; never double-apply an operation, lose an already committed operation silently, or report an unverified success. Corrupt alpha storage must not alter beta storage or prevent beta commits.

Do not corrupt a live CI runner's host filesystem or any non-disposable volume.

### 4.4 Resource faults

Apply bounded per-container CPU, memory, process, and disk/log quotas. Drive beta to each configured limit while measuring alpha's commit availability and latency. Record actual cgroup/container enforcement. If both networks share a runner/daemon, report that shared host as a common failure domain; the first topology avoids this by placing alpha and beta on separate runner VMs.

Do not claim OS-enforced isolation from Docker labels or directory names alone.

## 5. Test protocol and acceptance thresholds

The experiment must publish thresholds before its first run. Initial minimum protocol:

1. Start alpha and beta from distinct genesis manifests, each with four validators and unique test keys.
2. Verify each network independently reaches at least height 10.
3. Submit at least 100 deterministic transactions per project, including duplicate operation IDs, stale sequence, malformed envelopes, and cross-project replay attempts.
4. Export and independently verify evidence bundles for at least three non-genesis heights per project, including the final height.
5. Confirm alpha and beta app hashes, chain IDs, genesis digests, validator-set hashes, and transaction histories differ where expected.
6. Stop one beta validator; beta continues. Stop a second beta validator; beta stops committing. Alpha continues throughout.
7. Partition beta 2+2; neither partition advances. Restore connectivity; beta resumes one history without conflicting commits.
8. Stop all beta validators; alpha continues for at least five additional committed heights.
9. Corrupt alpha's disposable application state; alpha fails closed or follows the documented replay recovery; beta remains verifiable and continues.
10. Attempt all negative verifier cases; every case is rejected with the expected reason code.
11. Repeat the full baseline and fault sequence three times from fresh genesis data.

Hard acceptance criteria:
- zero conflicting commits at the same chain/height;
- zero cross-project transaction acceptance;
- zero cross-project app-state or storage mutation;
- zero accepted invalid proof bundles;
- zero critical commits without that project's quorum;
- no application sequence or idempotency divergence across validators;
- no alpha failure attributable to beta-only faults in the separate-runner topology;
- all recovery outcomes deterministic and captured;
- every run's exact binaries, configs, test commands, artifacts, and failures retained.

Performance thresholds (latency, resource caps, and recovery time) must be agreed before implementation based on the actual runner size. They cannot be retroactively relaxed to turn a failure into a pass. This document intentionally does not invent numeric performance budgets without a confirmed runner class.

## 6. Required artifacts

Each run must retain:
- exact source and binary digests;
- Go toolchain, OS/architecture, CometBFT version/commit, dependency SBOM;
- genesis manifests and validator public-key sets (never private keys);
- per-validator logs, WAL metadata, process exit codes, and restart chronology;
- transaction corpus and canonical bytes;
- per-height headers, commits, validator sets, app hashes, and verifier output;
- resource samples and fault-injection records;
- machine-readable summary with explicit PASS/FAIL/NOT RUN for every scenario.

Private validator keys must be generated uniquely for the run, remain within isolated test storage, never be uploaded as artifacts, and be destroyed with the disposable environment. No production secrets or persistent Tailscale credentials are needed for the initial separate-runner topology.

## 7. Go/no-go gates

**GO to implement the disposable harness** only after reviewers confirm:
- the exact ABCI interface and recovery behavior for the pinned release;
- deterministic state serialization and published test vectors;
- proof-bundle extraction and independent verification path;
- safe, bounded fault injection and artifact redaction;
- runner class and predeclared resource/performance thresholds;
- workflow opt-in, least-privilege permissions, and cleanup scope.

**NO-GO** if the verifier depends on the RPC node's assertion, if app state can advance without verified commit, if two validators can commit conflicting histories, if alpha and beta share a correctness-critical store/authority, or if the test requires production credentials or a hosted coordinator.

A GO here authorizes only a disposable test harness proposal; it does not select CometBFT for Zion, change the product's decentralization constraints, approve a global admission committee, or authorize merge/deploy/release.

## 8. Explicit non-claims

This specification is not an executed test, security review, production architecture approval, proof of independent operators, proof against Byzantine operators, proof of cloud-provider independence, or evidence that Zion's current runtime uses CometBFT. It does not implement a trust anchor, validator bootstrap/rotation, a global user-admission order, or the first-1,000 founder cohort.

## 9. Runner class and initial resource envelope (2026-11-15)

### 9.1 Repository and runner facts

The GitHub repository metadata reports visibility `public`. The existing private-runner connectivity workflow already uses the explicit `ubuntu-24.04` label. GitHub's current hosted-runner documentation lists standard Linux runners for public repositories with that label as a new VM with 4 vCPUs, 16 GB RAM, and 14 GB SSD. This capacity is different for private repositories; do not copy these numbers if repository visibility or runner class changes.

References:
- https://docs.github.com/en/actions/reference/runners/github-hosted-runners
- https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job

The PoC should pin `runs-on: ubuntu-24.04` rather than `ubuntu-latest`, and must record the actual runner image, kernel, architecture, CPU count, memory, available disk, Docker version, and cgroup mode at job start. If observed capacity differs from this envelope, abort before starting validators and mark the run NOT RUN.

### 9.2 Per-project runner budget

Apply the following conservative starting envelope independently to each project runner. These are test guardrails, not claims about production node sizing:

| Resource | Per validator (4 total) | Project-job ceiling / rule |
|---|---:|---:|
| CPU | 0.5 CPU quota | 2 CPU total for validators |
| Memory | 768 MiB hard limit | 3 GiB total for validators |
| PIDs | 128 | 512 total across validators |
| Container log | 16 MiB, 2 rotated files | 128 MiB combined maximum |
| Application process | n/a | 1 CPU, 1 GiB memory, 128 PIDs |
| Test corpus/state | n/a | 512 MiB maximum per project |
| Job wall time | n/a | 25 minutes hard timeout |
| Host disk reserve | n/a | Keep at least 3 GiB free; abort safely below this |

The job must leave capacity for the runner OS, Docker daemon, evidence collector, and fault controller. Measure actual usage rather than assuming container limits equal observed consumption. Use Docker CPU, memory, and PID limits plus bounded log rotation. The application must enforce the test-state/corpus byte ceiling before accepting more data.

A 14 GB runner disk is shared by the OS image, checkout, Docker layers, writable layers, volumes, logs, and artifacts. Do not claim a per-container hard disk quota merely because a volume has a size label. The harness must verify the actual backing filesystem and enforcement mechanism. If a hard per-volume quota cannot be demonstrated, use strict application-level byte limits, bounded logs, continuous free-space monitoring, and a 3 GiB host reserve; mark host disk-full fault injection NOT RUN unless it can be safely contained in a disposable size-limited filesystem.

### 9.3 Safe stress-test policy

The resource-pressure scenarios must be sequential, never simultaneous across all resource classes:

1. Capture a baseline with both projects healthy.
2. Apply one beta-only limit/stressor at a time.
3. Verify beta's own resource cap is enforced and its failure mode is recorded.
4. Continue measuring alpha independently for the entire beta stress interval.
5. Remove the stressor and verify beta recovers from its own state.
6. Reset to fresh genesis before the next stress class.

Do not run an unbounded fork bomb, host-wide disk fill, host memory exhaustion, or host CPU saturation. PID pressure is limited to the container's 128-PID cap. Disk-full testing must target a disposable capped filesystem or a deterministic application storage fault shim, never the runner root filesystem. If the mechanism cannot be isolated and proven, record NOT RUN rather than simulating it with a host-level destructive command.

### 9.4 Interpretation

These limits are a conservative harness envelope chosen for a public-repository standard Ubuntu runner, not performance acceptance thresholds for Zion. They do not establish that four validators per VM represent four independent operators. They also do not define production throughput, memory requirements, or a supported maximum number of projects per node.

Before the first implementation run, the workflow must print and validate the observed capacity, and the test report must retain both configured limits and measured peak CPU, RSS, PIDs, disk usage, log bytes, and free-space minimum. Any threshold adjustment after observing a failure requires a new reviewed specification revision and a fresh full run.
