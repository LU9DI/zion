# Zion committed-state machine contract (pre-ABCI)

Status: **architecture contract draft; not implemented and not a BFT claim**  
Scope: PR #68, branch `architecture/fully-decentralized-core`  
Purpose: define the application boundary that must exist before a CometBFT/ABCI integration or production admission migration can be considered.

## 1. Executive findings

The current repository contains useful deterministic and cryptographic primitives, but no canonical committed-state application:

- `src/project-governance.js` validates project-scoped governance proposals, threshold approvals, epochs, prior-state hashes, and new-governor proof of possession. Its own contract says the caller must commit the result through distributed BFT. A governance certificate authorizes a proposed transition; it is not a BFT commit certificate.
- `src/signed-project-event-log.js` is a node-local, single-writer signed journal. It chains and durably appends events, but does not choose canonical order across nodes.
- `src/signed-project-event-replica.js` durably observes per-signer event streams, rejects gaps/equivocation, and authenticates project authorization. It does not establish a globally agreed state or quorum finality.
- `src/signed-project-event-transport.js` provides authenticated one-hop replication and ACKs. An ACK proves durable receipt by that peer, not consensus commitment.
- `src/peer-admission-controller.js` is a single-process coordinator with local state, trusted-introducer vouchers, capacity checks, rollout caps, and a per-issuer quota. Its local queue and persistence are not a distributed transaction.
- `src/social-identity-directory.js` is a local profile directory; its proof establishes signing-key possession, not a globally unique person or globally committed username.
- `src/peer-introduction-vouchers.js` are node-introduction statements, not user invitations.
- `docs/USER_INVITATION_PROTOCOL_ADR.md` correctly requires invitation consumption, recipient admission, and founding ordinal assignment to occur in one canonical quorum-committed transition.

These components must not be wired together as though their combined behavior already provides consensus.

## 2. Scope boundary and unresolved global-admission conflict

The proposed BFT evaluation is project-scoped: independent projects have separate genesis manifests, validator committees, governance epochs, histories, and failure domains. The user-invitation ADR, however, defines one Zion-wide network/genesis identifier and one globally contiguous founding ordinal sequence from 1 through 1,000.

A project-scoped consensus instance cannot, by itself, assign a unique ordinal across all projects. Two independent committees could each observe fewer than 1,000 founders and concurrently assign the same next ordinal. A local cache, DHT, website counter, GitHub workflow, or single database would merely hide a central authority and is explicitly disallowed by the invitation ADR.

**This is an architecture blocker, not an implementation detail.** Before implementing user invitation redemption, Zion must explicitly choose one of these product/architecture directions:

1. Define a Zion-wide admission consensus domain that serializes invitation consumption and the founder counter. This is a global admission authority/committee even if it is not a global blockchain; it must be reconciled with the no-global-committee constraint and independently threat-modelled.
2. Change founding ordinal semantics to be project-scoped, or otherwise change the meaning of “first 1,000 Zion users.” This changes the product requirement and must not be done implicitly.
3. Specify and prove a different distributed allocation protocol that preserves globally unique, contiguous ordinals without a central committee or global serialization point. No such protocol is currently specified or implemented; do not assume that partitioning or deterministic hashing solves a contiguous global counter.

Until this conflict is resolved, project-level BFT can be evaluated independently, but global user admission/founding status must remain unavailable. Do not claim the project committee automatically solves Zion-wide admission.

## 3. State-machine boundary

The application state machine consumes bounded, versioned commands and a prior committed state. It must produce deterministic state changes and deterministic transaction results. The consensus engine decides the canonical order and finality of commands; the application must not invent a second consensus layer.

### 3.1 Command envelope (proposed contract)

Every state-changing command must carry:

- protocol version and command schema version;
- explicit scope: project ID, or a separately specified network-admission scope;
- stable operation ID generated by the caller and bounded to a fixed encoding/length;
- command type and bounded canonical payload;
- expected governance epoch and, where relevant, expected prior state hash;
- authenticated author identity and signature/proof required by that command;
- policy version and any deterministic expiry/validity bound.

The command must not use a node's local wall clock, local filesystem, local capacity sample, random generator, network lookup, environment variable, or iteration order as an input to a committed transition. Any time-dependent rule must define a consensus-provided time/height input and exact boundary semantics. Any randomness used by a protocol must be supplied through a separately specified, deterministic and consensus-compatible beacon; it must not call local randomness inside transition execution.

Unknown fields, oversized payloads, unsupported versions, malformed canonical encodings, and scope mismatches are rejected deterministically.

### 3.2 Logical execution stages

The implementation must distinguish:

1. **Ingress/precheck:** cheap syntax, size, signature-shape and rate checks. A precheck result is advisory only; it cannot authorize a mutation.
2. **Consensus proposal/order:** validators order commands under the selected BFT protocol.
3. **Deterministic state transition:** every honest application replica revalidates the command against the same prior committed state and consensus inputs, then computes the same result.
4. **Durable commit/recovery:** application state, operation result, state root, and any committed outbox record become durable under a documented atomicity contract consistent with the consensus engine's application interface.
5. **External effect delivery:** notifications, email, storage replication, UI updates, and other non-deterministic side effects are delivered after commit from a durable outbox. Delivery is at-least-once with idempotent effect IDs; delivery failure cannot roll back or alter committed state.

The exact CometBFT v0.38.26 ABCI++ callback mapping, commit response semantics, application database contract, and crash-recovery ordering still require a separate API/source audit before code is written. This document intentionally does not guess those details.

### 3.3 Idempotency and result semantics

The state machine needs a bounded, durable operation-result index:

- First use of an operation ID binds it to the canonical command digest and terminal result.
- Reuse with the same digest returns the original result and must not apply the mutation again.
- Reuse with a different digest is a deterministic conflict.
- A client timeout after submission is an unknown outcome until the client queries the committed operation ID; it must not trigger a fresh operation ID automatically.
- Retention, pruning, and snapshot rules for operation IDs must preserve the replay-safety horizon. No arbitrary eviction may make an old committed command executable again.

Open design item: decide whether deterministic rejected commands included in a committed block also consume/store their operation IDs, or whether only successful state transitions are idempotency-indexed. The choice affects retry semantics and state growth and must be fixed before implementation.

## 4. Minimum logical state domains

The following are logical state partitions, not a final database schema:

| Domain | Required committed data | Must not be treated as |
|---|---|---|
| Project metadata | project ID, genesis digest, protocol/schema version, current committed revision/state root | A global Zion registry |
| Project governance | governor keys, threshold, governance epoch, state hash | BFT validator set or BFT commit certificate |
| Validator membership | project-scoped validator identities, voting power, committee epoch, activation boundary | Proof that operators are independent people |
| Peer membership | project-scoped admitted/revoked peer identities and authorization epochs | User signup or global founding cohort |
| Operation results | operation ID, command digest, terminal result, committed revision | A local request cache |
| Outbox | committed effect ID, effect type, bounded payload/reference, delivery status managed outside deterministic state | A source of consensus decisions |

The project state root must bind all consensus-critical domains and be reproducible from the same ordered committed commands. Each project must have an independently verifiable genesis and state root.

User invitations and Zion-wide founder ordinals are intentionally not placed into the project state table until the scope conflict in section 2 is resolved.

## 5. Command families and authorization

### 5.1 Project governance

Existing governance operations are:

- `ADD_GOVERNOR`
- `ROTATE_GOVERNOR_KEY`
- `REVOKE_GOVERNOR`
- `SET_THRESHOLD`

The current module binds each proposal to project ID, next governance epoch, previous governance state hash, and action-specific data. Threshold approvals are checked against the current governor set. Adding/rotating a key also requires proof of possession; rotation requires the outgoing governor's approval.

Required integration rule: the governance transition is applied only as part of a BFT-ordered state transition. The threshold certificate is an authorization input. It does not substitute for consensus, determine canonical order, or prove that the new state is committed.

### 5.2 Project peer admission and revocation

The current peer admission controller must not be migrated verbatim into the consensus state machine:

- Trusted-introducer vouchers can remain an optional admission-policy input if the project governance policy explicitly selects them.
- The local capacity provider and rollout policy are node-local operational observations. They cannot independently decide globally committed membership, because different replicas can observe different capacity at the same logical time.
- The existing per-issuer quota is not automatically a product rule for user invitations. Do not carry it into the user invitation protocol.
- Local serialization and local state-store persistence are not distributed atomicity.

The future project command must specify the project, subject identity, authorization evidence, expected membership/governance epoch, operation ID, and deterministic policy result. Local nodes may separately decide whether they have enough resources to serve the peer, but that local serving decision must not rewrite canonical membership.

### 5.3 User invitations

The separate user-invitation ADR remains the authoritative product protocol for invitation behavior: unlimited invitations per admitted user, one-time redemption, revocation ordered against redemption, and atomic admission/founder assignment.

No current source file implements this protocol. Do not reuse node vouchers, local peer admission, or the project-governance module as a substitute. The global-vs-project consensus scope conflict must be resolved first.

## 6. Determinism, time, and cryptography

- Canonical serialization must be specified byte-for-byte, including Unicode policy, integer bounds, map ordering, duplicate-field handling, and domain separation. The existing governance canonicalizer is a useful local precedent but is not yet a cross-language protocol specification.
- All committed hashes must include explicit domain/version separation and the exact scope/genesis identifier.
- Signature verification must use the committed authorization state and exact command digest. A signature that was valid under a prior epoch must not silently authorize a command under a later epoch.
- Node-local wall clocks may be used for transport freshness or UI diagnostics, but not to decide committed expiry or admission. The current voucher and governance helpers use local `now` parameters; the ABCI transition must replace this with an explicit deterministic consensus input.
- Local randomness may generate invitation secrets, request IDs, or ephemeral transport material before submission. Any value that affects committed state must be included in the signed command and validated deterministically.
- Key proof establishes control of a key, not operator independence, real-world uniqueness, or Sybil resistance.

## 7. Atomicity, storage, and crash recovery

The committed application adapter must define and test:

1. atomic visibility of the new state, operation-result entry, and outbox record;
2. durable write ordering and fsync/transaction semantics;
3. behavior if the process crashes before, during, or after the consensus engine's commit boundary;
4. deterministic replay after restart from the last committed state;
5. snapshot creation, verification, restore, and schema migration;
6. WAL/state reconciliation and refusal to serve writes if the application state is ahead of or behind the consensus commit point;
7. disk-full, partial-write, fsync, corruption, and ambiguous-commit behavior;
8. bounded state growth and safe compaction without losing replay protection.

The current signed event journal's append/fsync/rollback behavior is valuable local durability evidence, but it is not an application database transaction and cannot atomically commit a BFT block, application state, operation result, and external effect. The replica journal is an observation store, not canonical committed state.

No shared PostgreSQL/Neon database may be the hidden source of truth for the final architecture. Transitional PostgreSQL code must remain untouched until a replacement passes parity, recovery, and failure-isolation tests.

## 8. Read consistency and client behavior

- Security-critical reads must identify the project/network scope, committed revision/height, state root, and freshness evidence.
- A stale replica may serve explicitly labelled stale, non-authoritative data, but may not authorize new writes or claim current membership.
- A client receiving an ambiguous submission result must query by operation ID before retrying.
- A client must distinguish `accepted for proposal`, `included in a block`, `committed`, and `externally delivered`. The UI must never show “admitted” or “invitation redeemed” based solely on local enqueue or a peer ACK.
- If quorum is unavailable, critical writes fail closed. No local cache, PostgreSQL fallback, hosted API, or single peer may commit on behalf of the committee.

## 9. Required verification gates before implementation

1. Resolve the global user-invitation/founding-ordinal scope conflict.
2. Audit the exact pinned CometBFT ABCI++ API and v0.38.26 application commit/recovery contract.
3. Freeze canonical command encoding and cross-language test vectors.
4. Specify state schema, state-root computation, operation-result retention, rejected-operation idempotency, and outbox delivery semantics.
5. Specify deterministic time/height and any randomness/beacon inputs.
6. Implement a storage-neutral deterministic transition module with no network, filesystem, wall-clock, or environment access.
7. Test same-input/same-state determinism across independent processes and supported runtimes.
8. Only then integrate the module with a disposable CometBFT test harness under the separate VM/network safety gate in `docs/COMETBFT_PROJECT_ISOLATION_FEASIBILITY_SPIKE.md`.
9. Prove partition, quorum loss, restart, WAL recovery, validator reconfiguration, and cross-project isolation before runtime integration.
10. Keep invitation redemption, official launcher migration, and removal of transitional PostgreSQL disabled until their own gates pass.

## 10. Non-claims and current state

- This is a design contract, not implementation or a formal safety proof.
- No CometBFT dependency, ABCI application, storage adapter, outbox worker, or runtime integration is added.
- Existing governance approvals are not BFT certificates.
- Existing signed event replication is not consensus or canonical committed state.
- Project-scoped committees do not currently provide a Zion-wide founder counter.
- No global user invitation is safe to redeem until its consensus scope is decided and implemented.
- No merge, deployment, release, database mutation, migration, or production key operation is authorized by this document.
