# Zion committed-state machine contract (pre-ABCI)

Status: **architecture contract draft; not implemented and not a BFT claim**  
Scope: PR #68, branch `architecture/fully-decentralized-core`  
Purpose: define the application boundary that must exist before a CometBFT/ABCI integration or production admission migration can be considered.

## 1. Executive findings

The current repository contains useful deterministic and cryptographic primitives, but no canonical committed-state application:

- `src/project-governance.js` validates project-scoped governance proposals, threshold approvals, epochs, prior-state hashes, and new-governor proof of possession. Its own contract says the caller must commit the result through distributed BFT. A governance certificate authorizes a proposed transition; it is not a BFT commit certificate.
- `src/signed-project-event-log.js` is a node-local, single-writer signed journal. It chains and durably appends events, but does not choose canonical order across nodes.
- `src/signed-project-event-replica.js` durably observes per-signer event streams, rejects gaps/equivocation, and authenticates project authorization. It does not establish a globally agreed state or quorum finality.
- `src/signed-project-event-transport.js` provides authenticated one-hop replication and ACKs. An ACK proves durable receipt by that peer, not consensus commitment.
- `src/peer-admission-controller.js` is a single-process coordinator with local state, trusted-introducer vouchers, capacity checks, rollout caps, and a per-issuer quota. Its local queue and persistence are not a distributed transaction.
- `src/social-identity-directory.js` is a local profile directory; its proof establishes signing-key possession, not a globally unique person or globally committed username.
- `src/peer-introduction-vouchers.js` are node-introduction statements, not user invitations.
- `docs/USER_INVITATION_PROTOCOL_ADR.md` correctly requires invitation consumption, recipient admission, and founding ordinal assignment to occur in one canonical quorum-committed transition.

These components must not be wired together as though their combined behavior already provides consensus.

## 2. Scope boundary and unresolved global-admission conflict

The proposed BFT evaluation is project-scoped: independent projects have separate genesis manifests, validator committees, governance epochs, histories, and failure domains. The user-invitation ADR, however, defines one Zion-wide network/genesis identifier and one globally contiguous founding ordinal sequence from 1 through 1,000.

A project-scoped consensus instance cannot, by itself, assign a unique ordinal across all projects. Two independent committees could each observe fewer than 1,000 founders and concurrently assign the same next ordinal. A local cache, DHT, website counter, GitHub workflow, or single database would merely hide a central authority and is explicitly disallowed by the invitation ADR.

**This is an architecture blocker, not an implementation detail.** Before implementing user invitation redemption, Zion must explicitly choose one of these product/architecture directions:

1. Define a Zion-wide admission consensus domain that serializes invitation consumption and the founder counter. This is a global admission authority/committee even if it is not a global blockchain; it must be reconciled with the no-global-committee constraint and independently threat-modelled.
2. Change founding ordinal semantics to be project-scoped, or otherwise change the meaning of “first 1,000 Zion users.” This changes the product requirement and must not be done implicitly.
3. Specify and prove a different distributed allocation protocol that preserves globally unique, contiguous ordinals without a central committee or global serialization point. No such protocol is currently specified or implemented; do not assume that partitioning or deterministic hashing solves a contiguous global counter.

Until this conflict is resolved, project-level BFT can be evaluated independently, but global user admission/founding status must remain unavailable. Do not claim the project committee automatically solves Zion-wide admission.

## 3. State-machine boundary

The application state machine consumes bounded, versioned commands and a prior committed state. It must produce deterministic state changes and deterministic transaction results. The consensus engine decides the canonical order and finality of commands; the application must not invent a second consensus layer.

### 3.1 Command envelope (proposed contract)

Every state-changing command must carry:

- protocol version and command schema version;
- explicit scope: project ID, or a separately specified network-admission scope;
- stable operation ID generated by the caller and bounded to a fixed encoding/length;
- command type and bounded canonical payload;
- expected governance epoch and, where relevant, expected prior state hash;
- authenticated author identity and signature/proof required by that command;
- policy version and any deterministic expiry/validity bound.

The command must not use a node's local wall clock, local filesystem, local capacity sample, random generator, network lookup, environment variable, or iteration order as an input to a committed transition. Any time-dependent rule must define a consensus-provided time/height input and exact boundary semantics. Any randomness used by a protocol must be supplied through a separately specified, deterministic and consensus-compatible beacon; it must not call local randomness inside transition execution.

Unknown fields, oversized payloads, unsupported versions, malformed canonical encodings, and scope mismatches are rejected deterministically.

### 3.2 Logical execution stages

The implementation must distinguish:

1. **Ingress/precheck:** cheap syntax, size, signature-shape and rate checks. A precheck result is advisory only; it cannot authorize a mutation.
2. **Consensus proposal/order:** validators order commands under the selected BFT protocol.
3. **Deterministic state transition:** every honest application replica revalidates the command against the same prior committed state and consensus inputs, then computes the same result.
4. **Durable commit/recovery:** application state, operation result, state root, and any committed outbox record become durable under a documented atomicity contract consistent with the consensus engine's application interface.
5. **External effect delivery:** notifications, email, storage replication, UI updates, and other non-deterministic side effects are delivered after commit from a durable outbox. Delivery is at-least-once with idempotent effect IDs; delivery failure cannot roll back or alter committed state.

The exact CometBFT v0.38.26 ABCI++ callback mapping, commit response semantics, application database contract, and crash-recovery ordering still require a separate API/source audit before code is written. This document intentionally does not guess those details.

### 3.3 Idempotency and result semantics

The state machine needs a bounded, durable operation-result index:

- First use of an operation ID binds it to the canonical command digest and terminal result.
- Reuse with the same digest returns the original result and must not apply the mutation again.
- Reuse with a different digest is a deterministic conflict.
- A client timeout after submission is an unknown outcome until the client queries the committed operation ID; it must not trigger a fresh operation ID automatically.
- Retention, pruning, and snapshot rules for operation IDs must preserve the replay-safety horizon. No arbitrary eviction may make an old committed command executable again.

Open design item: decide whether deterministic rejected commands included in a committed block also consume/store their operation IDs, or whether only successful state transitions are idempotency-indexed. The choice affects retry semantics and state growth and must be fixed before implementation.

## 4. Minimum logical state domains

The following are logical state partitions, not a final database schema:

| Domain | Required committed data | Must not be treated as |
|---|---|---|
| Project metadata | project ID, genesis digest, protocol/schema version, current committed revision/state root | A global Zion registry |
| Project governance | governor keys, threshold, governance epoch, state hash | BFT validator set or BFT commit certificate |
| Validator membership | project-scoped validator identities, voting power, committee epoch, activation boundary | Proof that operators are independent people |
| Peer membership | project-scoped admitted/revoked peer identities and authorization epochs | User signup or global founding cohort |
| Operation results | operation ID, command digest, terminal result, committed revision | A local request cache |
| Outbox | committed effect ID, effect type, bounded payload/reference, delivery status managed outside deterministic state | A source of consensus decisions |

The project state root must bind all consensus-critical domains and be reproducible from the same ordered committed commands. Each project must have an independently verifiable genesis and state root.

User invitations and Zion-wide founder ordinals are intentionally not placed into the project state table until the scope conflict in section 2 is resolved.

## 5. Command families and authorization

### 5.1 Project governance

Existing governance operations are:

- `ADD_GOVERNOR`
- `ROTATE_GOVERNOR_KEY`
- `REVOKE_GOVERNOR`
- `SET_THRESHOLD`

The current module binds each proposal to project ID, next governance epoch, previous governance state hash, and action-specific data. Threshold approvals are checked against the current governor set. Adding/rotating a key also requires proof of possession; rotation requires the outgoing governor's approval.

Required integration rule: the governance transition is applied only as part of a BFT-ordered state transition. The threshold certificate is an authorization input. It does not substitute for consensus, determine canonical order, or prove that the new state is committed.

### 5.2 Project peer admission and revocation

The current peer admission controller must not be migrated verbatim into the consensus state machine:

- Trusted-introducer vouchers can remain an optional admission-policy input if the project governance policy explicitly selects them.
- The local capacity provider and rollout policy are node-local operational observations. They cannot independently decide globally committed membership, because different replicas can observe different capacity at the same logical time.
- The existing per-issuer quota is not automatically a product rule for user invitations. Do not carry it into the user invitation protocol.
- Local serialization and local state-store persistence are not distributed atomicity.

The future project command must specify the project, subject identity, authorization evidence, expected membership/governance epoch, operation ID, and deterministic policy result. Local nodes may separately decide whether they have enough resources to serve the peer, but that local serving decision must not rewrite canonical membership.

### 5.3 User invitations

The separate user-invitation ADR remains the authoritative product protocol for invitation behavior: unlimited invitations per admitted user, one-time redemption, revocation ordered against redemption, and atomic admission/founder assignment.

No current source file implements this protocol. Do not reuse node vouchers, local peer admission, or the project-governance module as a substitute. The global-vs-project consensus scope conflict must be resolved first.

## 6. Determinism, time, and cryptography

- Canonical serialization must be specified byte-for-byte, including Unicode policy, integer bounds, map ordering, duplicate-field handling, and domain separation. The existing governance canonicalizer is a useful local precedent but is not yet a cross-language protocol specification.
- All committed hashes must include explicit domain/version separation and the exact scope/genesis identifier.
- Signature verification must use the committed authorization state and exact command digest. A signature that was valid under a prior epoch must not silently authorize a command under a later epoch.
- Node-local wall clocks may be used for transport freshness or UI diagnostics, but not to decide committed expiry or admission. The current voucher and governance helpers use local `now` parameters; the ABCI transition must replace this with an explicit deterministic consensus input.
- Local randomness may generate invitation secrets, request IDs, or ephemeral transport material before submission. Any value that affects committed state must be included in the signed command and validated deterministically.
- Key proof establishes control of a key, not operator independence, real-world uniqueness, or Sybil resistance.

## 7. Atomicity, storage, and crash recovery

The committed application adapter must define and test:

1. atomic visibility of the new state, operation-result entry, and outbox record;
2. durable write ordering and fsync/transaction semantics;
3. behavior if the process crashes before, during, or after the consensus engine's commit boundary;
4. deterministic replay after restart from the last committed state;
5. snapshot creation, verification, restore, and schema migration;
6. WAL/state reconciliation and refusal to serve writes if the application state is ahead of or behind the consensus commit point;
7. disk-full, partial-write, fsync, corruption, and ambiguous-commit behavior;
8. bounded state growth and safe compaction without losing replay protection.

The current signed event journal's append/fsync/rollback behavior is valuable local durability evidence, but it is not an application database transaction and cannot atomically commit a BFT block, application state, operation result, and external effect. The replica journal is an observation store, not canonical committed state.

No shared PostgreSQL/Neon database may be the hidden source of truth for the final architecture. Transitional PostgreSQL code must remain untouched until a replacement passes parity, recovery, and failure-isolation tests.

## 8. Read consistency and client behavior

- Security-critical reads must identify the project/network scope, committed revision/height, state root, and freshness evidence.
- A stale replica may serve explicitly labelled stale, non-authoritative data, but may not authorize new writes or claim current membership.
- A client receiving an ambiguous submission result must query by operation ID before retrying.
- A client must distinguish `accepted for proposal`, `included in a block`, `committed`, and `externally delivered`. The UI must never show “admitted” or “invitation redeemed” based solely on local enqueue or a peer ACK.
- If quorum is unavailable, critical writes fail closed. No local cache, PostgreSQL fallback, hosted API, or single peer may commit on behalf of the committee.

## 9. Required verification gates before implementation

1. Resolve the global user-invitation/founding-ordinal scope conflict.
2. Audit the exact pinned CometBFT ABCI++ API and v0.38.26 application commit/recovery contract.
3. Freeze canonical command encoding and cross-language test vectors.
4. Specify state schema, state-root computation, operation-result retention, rejected-operation idempotency, and outbox delivery semantics.
5. Specify deterministic time/height and any randomness/beacon inputs.
6. Implement a storage-neutral deterministic transition module with no network, filesystem, wall-clock, or environment access.
7. Test same-input/same-state determinism across independent processes and supported runtimes.
8. Only then integrate the module with a disposable CometBFT test harness under the separate VM/network safety gate in `docs/COMETBFT_PROJECT_ISOLATION_FEASIBILITY_SPIKE.md`.
9. Prove partition, quorum loss, restart, WAL recovery, validator reconfiguration, and cross-project isolation before runtime integration.
10. Keep invitation redemption, official launcher migration, and removal of transitional PostgreSQL disabled until their own gates pass.

## 10. Pinned CometBFT v0.38.26 ABCI++ source audit (2026-11-14)

The exact tag `v0.38.26` was inspected through the upstream source files below. This is a source/API audit, not a compiled integration or crash-test result.

### Interface and deterministic execution boundary

The pinned `abci/types/application.go` declares the full `Application` interface:
`Info`, `Query`, `CheckTx`, `InitChain`, `PrepareProposal`, `ProcessProposal`, `FinalizeBlock`, `ExtendVote`, `VerifyVoteExtension`, `Commit`, and the four snapshot methods.

The application must treat these methods differently:

- `PrepareProposal` and `ProcessProposal` may be called repeatedly across rounds for the same height. Any speculative execution must remain a candidate state; it must not mutate the canonical working state.
- `ExtendVote` and `VerifyVoteExtension` must not mutate application state. Vote-extension data may influence a later proposal only through deterministic, explicitly supplied inputs.
- `FinalizeBlock` receives the decided block and performs deterministic execution. It must not durably commit application state.
- `Commit` is the only ABCI callback in which the application persists the resulting state. The application must retain the last successfully committed height so `Info` can report the correct recovery point.
- `CheckTx` is a mempool admission check, not an authorization/commit decision. It must not be used as the canonical state transition.
- Queries and any external RPC surface must not expose mutable state that can bypass the ABCI execution boundary.

### Exact block/commit ordering in the pinned implementation

In `state/execution.go`, `BlockExecutor.applyBlock` performs the following sequence:

1. Calls application `FinalizeBlock` with the decided block.
2. Checks that the number of transaction results matches the block transaction count.
3. Saves the `FinalizeBlock` response in CometBFT's state store.
4. Applies validator/consensus-parameter updates to the CometBFT state.
5. Calls `BlockExecutor.Commit`.
6. Inside `Commit`, locks the mempool, flushes outstanding mempool ABCI requests, invokes application `Commit`, then updates the mempool.
7. After application commit succeeds, saves the updated CometBFT state (including the app hash from `FinalizeBlock` response).

Important consequences:

- In this release, `ResponseFinalizeBlock.app_hash` is the deterministic application state hash carried into CometBFT's next state/header. `ResponseCommit` supplies `retain_height`; do not design the application around a new app hash being returned by `Commit`.
- The application must atomically persist its own state, committed height, operation-result index, and committed outbox entries before `Commit` returns. A partial success must be detected and recovered without serving writes from an ambiguous state.
- CometBFT's block store, its saved finalize response/state, and the application's own commit are separate durable steps, not one cross-database transaction. Recovery behavior must explicitly handle crashes between them.
- Never call synchronous `/broadcast_tx` or `/broadcast_tx_sync` from the sequential logic of application `Commit`: CometBFT holds the mempool lock and this can deadlock.
- External notifications, email, webhooks, and other side effects must not execute as part of deterministic transition/commit. Persist an outbox item in the same application transaction and deliver it asynchronously with stable idempotency keys.

### Recovery, replay, and candidate-state constraints

The pinned `spec/abci/abci++_comet_expected_behavior.md` defines recovery as `Info` followed by consensus execution/replay. Each height follows zero or more consensus rounds, then `FinalizeBlock`, then `Commit`. A correct application must handle non-happy-path call sequences rather than assuming one proposal per height.

The pinned `spec/abci/abci++_app_requirements.md` documents that:

- `FinalizeBlock` transitions working state but must not persist it; persistence belongs in `Commit`.
- Candidate states produced during proposal processing are separate from the canonical execution state. Their number can grow across rounds, so memory use must be bounded and candidates may be discarded and re-executed.
- The application reports its last successfully committed height through `Info`; CometBFT replays blocks when its durable block/state records are ahead of the application.
- CometBFT can detect several out-of-order height conditions and panic. The application must never claim a height newer than the last state it durably committed.
- The application should not expose mutable state outside the ABCI connections; route authoritative reads through the application query boundary or a separately proven read-only snapshot.

### Required Zion adapter contract

Before implementation, the adapter design must now include these explicit rules:

1. Keep three distinct state views: committed durable state; current deterministic execution state for the decided height; and bounded, disposable candidate states for proposal evaluation.
2. Make `FinalizeBlock` deterministic and side-effect-free outside in-memory candidate/execution state. Use only prior committed state and values in the decided block/request. No local wall clock, network calls, environment-dependent reads, random generation, or external database reads may affect its result.
3. Compute the application state root deterministically from the post-transition state in `FinalizeBlock`; persist the exact corresponding state during `Commit`.
4. In one durable application transaction, persist the new state, height, operation IDs/results, and outbox records. Commit/flush that transaction before returning from ABCI `Commit`.
5. On startup, `Info` must report exactly the application's last durable committed height and app hash. If durable records disagree, are corrupt, or are ambiguous, stop critical writes and require deterministic replay/recovery; never advance locally.
6. Do not run side effects in `FinalizeBlock`, `Commit`, proposal callbacks, or vote-extension callbacks. A separate outbox worker may deliver effects after commit; it must tolerate duplicate delivery.
7. Add process-kill fault injection at each boundary: before/after FinalizeBlock response persistence, before application transaction, during transaction, after durable app commit but before CometBFT state save, and after state save. Verify recovery always converges to one state root and never repeats a committed mutation.
8. Test proposal-round churn and candidate eviction under memory limits; correctness must not depend on a candidate surviving until decision.
9. Test snapshot import/export against app hash, committed height, operation-index retention, and outbox replay semantics.

### Audit conclusion

The v0.38.26 interface is compatible with the planned deterministic state-machine boundary, but it does not provide an atomic transaction spanning CometBFT's block/state stores and the application's own database. Zion must implement and fault-test the application-side commit/replay contract described above. This audit does not select CometBFT for production, add a dependency, implement an ABCI application, prove two-project isolation, or authorize runtime integration.

## 12. Existing durable journal reuse assessment (2026-11-14)

Inspected the current `src/signed-project-event-log.js`, `src/signed-project-event-replica.js`, and `test/signed-project-event-log.test.js`.

### Reusable engineering mechanisms

The local event log already provides useful, tested mechanisms:

- A single-writer lock that fails closed when a lock exists; automatic stale-lock deletion is disabled.
- Serialized appends within one process.
- Bounded journal size and record count.
- Hash-chained, signed records and startup verification.
- Full-write loops, file `fsync`, directory `fsync` when the journal is first created.
- Rollback to the descriptor's original size after append I/O errors, followed by poisoning the instance until close/recovery.
- Startup rejection of incomplete trailing records, malformed JSON, identity mismatch, sequence gaps, and hash-chain mismatch.

The replica has analogous durable receiver mechanics, but it is explicitly a replication journal and not a commitment authority.

### Why direct reuse is not approved

The existing log is scoped to one node identity and one local sequence. It is not a transaction manager for the committed application projection, does not atomically coordinate multiple projection indexes, and does not establish quorum commitment. Its replica accepts authenticated contiguous events but does not decide which events are final.

A possible future adapter could append one complete, canonical block-commit envelope per height (including state delta or snapshot reference, app hash, operation results, and outbox entries) as a single durable record, then rebuild projections by replay. That would require a separate record schema, application-level validation, replay rules, compaction/snapshot protocol, key-lifecycle decision, and dedicated fault-injection tests. Reusing the existing event type or treating its local sequence as a consensus height would be incorrect.

### Decision

Reuse only the journal's proven low-level durability patterns as implementation references. Do not directly wire `SignedProjectEventLog` or `SignedProjectEventReplica` into ABCI `Commit`, do not relabel replicated events as committed state, and do not change production startup paths.

Next gate: prototype a separate append-only committed-block journal in the test area, or select a transactional embedded store after a dependency/runtime compatibility review. The prototype must be tested with real process termination and restart; in-memory fault injection is insufficient.


## 13. Durable committed-block journal prototype (2026-11-14)

A separate test-support prototype now exists at:

- `test/support/durable-committed-block-journal.js`
- `test/durable-committed-block-journal.test.js`

The prototype is deliberately outside `src/` and is not imported by production startup or runtime modules.

### Record and recovery contract

- One complete canonical JSONL record is appended per committed height.
- Each record contains the height, previous journal-record hash, application state root, full committed snapshot (state data, operation-result index, and outbox), and its own domain-separated record hash.
- Lock creation and journal appends use full-write loops; the journal also uses a single-writer exclusive lock, bounded total size, file `fsync`, and directory `fsync` when the lock or journal file is first created.
- Any ambiguous append or append-descriptor-close failure poisons the live instance; it cannot continue appending until it is closed and the journal is reopened and fully verified. Lock-descriptor close is tracked separately: the instance is not marked closed until lock cleanup completes, allowing a retry after a cleanup error without attempting to close an already-closed descriptor.
- Recovery verifies contiguous heights, previous-record hash links, application state roots, and record hashes before exposing the latest snapshot.
- Retrying an identical commit at the current height returns an idempotent already-committed result; a different state at that height is rejected as a commit conflict.
- An incomplete trailing line or any invalid record fails closed; the prototype does not silently truncate or skip uncertain history.
- A test-only crash hook exits the child process immediately after the record's `fsync`, before in-memory state is advanced. The restart test explicitly clears the abandoned lock only after the child has exited and the test has verified that no writer remains.

### Test coverage authored

1. Append, close, reopen, and recover the complete snapshot; reject a concurrent writer.
2. Terminate a separate Node process immediately after `fsync`, then recover the committed height and state after restart.
3. Reject incomplete trailing bytes, a tampered state snapshot, and a modified journal-record hash.
4. Reject height gaps and stale-lock cleanup without explicit no-writer verification.
5. Retry an identical commit at the same height idempotently; reject a conflicting state at that height, including after reopen.
6. Commit multiple heights and verify the full hash chain and latest recovered projection.
7. Inject failures before writing, after a partial write, before `fsync`, and after `fsync`; verify rollback, writer poisoning, and empty-state recovery after reopen.
8. Reject an existing symbolic-link journal path and verify its target and lock cleanup remain untouched; this preflight check is not race-free against concurrent path replacement.



The new `faultAt` cases are deterministic test hooks that throw at selected write boundaries. The partial-write case deliberately writes half of a serialized record before injecting the error, and the test verifies the file is truncated back to its original zero-byte length. They validate the prototype's rollback/poison/reopen control flow; they do **not** emulate kernel-level short writes, a real `fsync` error, disk-full behavior, controller-cache loss, or power failure.

### Strict limitations

This is an experimental, test-only append-only persistence prototype—not a production adapter and not evidence of consensus or quorum finality. The child-process test is authored but must be run by Node CI before it can be called passing. The final journal component is now opened through a file descriptor with `O_NOFOLLOW` where the platform exposes it, and the opened descriptor must identify a regular file; reads are performed through that descriptor rather than reopening the path. Platforms without `O_NOFOLLOW` fail closed instead of silently using a race-prone fallback. This narrows the final-component symlink/TOCTOU risk, but does not protect symlinked or concurrently replaced parent directories, prove safe directory traversal, or establish behavior under physical power loss, filesystem/controller write-cache failure, disk-full conditions, cross-platform directory-`fsync` differences, multi-process recovery races, snapshots/compaction, or long-term storage growth.

The stale-lock cleanup API requires an explicit caller assertion that no writer is active; it is not an automatic liveness detector. A production implementation needs an operator-safe recovery procedure and stronger cross-platform lock design.

### Gate

Do not wire this prototype into ABCI `Commit`, production startup, invitation redemption, or network membership. Before considering an adapter, run the full test suite and syntax checks on supported Node versions and operating systems; extend fault injection to actual short-write and filesystem-error conditions, disk-full behavior, process termination at every write boundary, and restart after each boundary; define snapshot/compaction and retention; and obtain independent review of filesystem and lock semantics.

before this prototype can be used outside its test scope.

A further lock-path limitation was identified during source review: `close()`
reads the lock's token/PID and then unlinks the pathname. The sequential
replacement-lock test proves that a replacement already present at read time
is preserved, but it does not close the race in which another process replaces
the path between the ownership read and `unlinkSync`. Node's current path-based
unlink operation does not provide an atomic "unlink only if this directory
entry still refers to the verified inode" guarantee. Parent-directory
replacement and hostile directory traversal are also outside this prototype's
proven guarantees. These limitations must remain explicit; do not describe
lock cleanup or path handling as race-free.


### Bounded recovery-read hardening (2026-11-14)

Source review found that the earlier implementation called `readFileSync(fd)`
and checked `maxBytes` only after the entire journal had been loaded into
memory. A file larger than the configured limit could therefore cause
unbounded allocation before the intended size guard ran.

The recovery path now reads from the already-open, no-follow file descriptor in
bounded 64 KiB chunks and stops as soon as it observes byte `maxBytes + 1`.
It rejects the journal with `ZION_JOURNAL_TOO_LARGE` before parsing any record.
A regression test writes a 1,025-byte file and opens it with a 1,024-byte limit;
it expects the size error and verifies that the constructor cleans up its own
lock. This bounds the recovery read buffer to the configured limit plus one
byte (apart from bounded chunk-list overhead), rather than trusting the
on-disk file size.

This is a test-support hardening change only. It does not resolve hostile
parent-directory traversal, the lock unlink TOCTOU window, power-loss
semantics, or consensus/finality requirements.
